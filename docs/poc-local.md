# ローカルPoCの実行と確認

Markdownの表示・タスク・ホワイトボードを、開発機で実NLIと接続して確認する手順。設計判断と部署展開との区別は[ADR-0008](adr/0008-local-poc-workflows.md)と[ADR-0009](adr/0009-feature-packages-and-subject-change.md)、対象と完了条件は[MVP](../MVP.md)を参照する。

入口（BFF・自然言語UI）はルートの`src/`、業務機能は`packages/features/`（`markdown`・`tasks`・`whiteboard`と、DBの接続・マイグレーションを含む共通部品の`kit`）、独立したIntent判定は`packages/core/`に置き、ビルド結果は`dist/`に出力する。業務画面は遅延読み込みのチャンクとして`dist/public/assets/`へ分かれる。依存定義を変えたブランチへ切り替えたときは、devShellで`make app-setup-offline`（取得済みでない依存があれば`make app-setup`）を実行して依存リンクを更新する。起動中のアプリには構成変更が反映されないため、Ctrl+Cで停止してから`make app-dev`で起動し直す。

テストは実装から分け、ルートの`tests/`に入口のAPI・ログ、`tests/web/`に画面、`tests/scripts/`に実行・検証スクリプトのテストを置く。コアと業務機能のテストは、それぞれのパッケージの`tests/`で管理する。型検査・lintにはテストも含め、製品のビルド対象は実装だけとする。

worktreeで作業する場合も、pnpmのストア・メタデータキャッシュと実NLIのモデルは本体のチェックアウトの`.local-poc/`・`.local-jev/`を共有する。

## `.local-poc`の用途

開発機での実行データと作業用キャッシュの保存先で、アプリのソースコードは置かない。Gitの管理対象外。

| 内容 | 用途 |
| --- | --- |
| `app.sqlite` | タスク画面で追加した自分のタスクと、保存したホワイトボード。適用済みのマイグレーションを`schema_migrations`に記録する（以前の申請データのテーブルが残っていても読み書きしない） |
| `http-verification.json`など | 分類プローブ・接続診断・Web配信確認の結果 |
| `pnpm-store/`・`cache/` | 取得済み依存などのキャッシュ（worktreeでは本体の`.local-poc/`のものを使う） |
| `config/`・`state/` | 利用者の認証設定から分離した依存管理用の作業領域 |

丸ごと削除すると保存済みのタスク・ボードも失われる。タスクとボードだけ空に戻す場合は、アプリ停止後に`make app-reset`を使う。

表は、アプリの起動時と`make app-reset`の前に、未適用のマイグレーションで作成・変更する。以前の版で作った表は、そのまま引き継ぐ。DBを開けない場合やマイグレーションに失敗した場合は、`db_setup_failed`を記録して起動を中止する（[ADR-0010](adr/0010-shared-db-and-migrations.md)）。

## 準備と起動

リポジトリのルートでdevShellへ入り、公開npm依存を取得する。direnvでdevShellが有効なら`nix develop`は不要。`app-setup`はネットワークを使い、依存のインストールスクリプトは実行しない。

```sh
nix develop
make app-setup
```

local-jevが未導入の場合だけ、次を実行する。Python依存の取得にネットワークを使う。

```sh
make jev-local-setup
```

固定revisionの重み・tokenizerが未準備なら、次を実行する。`jev-local-pin-model`は必要なファイルを取得し、ローカルのモデルカードを固定snapshotへ向ける。取得・保存にはネットワークとディスク容量が必要。[固定revisionの説明](jev-connection-check.md#実測revisionの重みとtokenizerの再取得)も参照する。

```sh
make jev-local-pin-model
```

アプリと推論サーバーをまとめて起動する。

```sh
make app-dev
```

不足するサービスだけを起動し、推論サーバーの準備完了まで待ってからアプリを使える状態にする。推論サーバーを起動した場合は、URLを案内する前に、inuiと同じ形の判定を1回行う（起動直後の最初の判定が遅いため。下記の「起動直後の判定の時間」）。モデル・重みは取得済みのものだけを使い、起動時に外部へダウンロードしない。起動済みの正常なサービスは再利用する。アプリは`/api/health`が返すビルドの識別子（`dist/`の場所と、`dist/server.js`・`dist/public/app.js`・`dist/public/app.css`・実行時に読み込むコアの`packages/core/dist/index.js`のハッシュ）が手元のビルドと一致する場合だけ再利用する。本体と`.worktrees/`のように別のチェックアウトで起動したアプリが同じポートで動いている場合は、再利用せずに停止を案内するので、そのアプリの起動端末でCtrl+Cを押してから起動し直す。

このターミナルを開いたまま、ブラウザで次を開く。終了はCtrl+Cで、このコマンドが起動したプロセスだけを停止する。再利用した既存プロセスは停止しない。

- 自然言語UI: [http://127.0.0.1:8766/](http://127.0.0.1:8766/)
- 比較用の旧形式: [http://127.0.0.1:8766/legacy](http://127.0.0.1:8766/legacy)

アプリの既定ポートは8766。`make app-dev`・`app-run`・`app-smoke`・`app-probe`・`app-diagnose`・`app-web-diagnose`は、環境変数の指定がなければすべて同じポートを使う。以前の3000番で起動したアプリが残っている場合は、その起動端末でCtrl+Cを押して停止する。既定値を変更しても起動済みのプロセスは停止しない。

待ち受けはIPv4 loopbackで、HostとPOSTのOriginはアプリのポートに照合する。推論サーバーは8765番を使う。検証用のポート指定`INUI_POC_PORT`（1024〜65535の整数）も利用できるが、通常は指定せず8766を使う。指定した場合は、そのアプリへの診断やプローブにも同じ値を付ける。

2026-11-11、3000番ではWindowsから応答がなかった利用者環境で、8766番への切替後にブラウザの画面表示成功が報告された。3000番の根本原因は未確定だが、この環境では8766番で操作確認を続けられる。

どちらも同じ業務API・画面・データを使う。自然言語UIは入力欄から画面を選び、旧形式はメニューから同じ画面を開く。業務画面はどちらも、細いヘッダーの下の画面全体に表示する。自然言語UIの入力欄は、最初は画面の中央にあり、業務画面を開いた後は右下のボタンから開くパネルにしまう（パネルはEscか「×」で閉じる）。パネルには入力と結果の履歴を表示し、再読み込みで消える。旧形式では、ヘッダーの「← メニューに戻る」でメニューへ戻る。アプリは固定のローカルNLIを呼び、公式APIキーの設定有無では切り替えない。従来の`make jev-probe`は別の検証用プローブであり、アプリの呼び出し経路には使わない。

## GitHubとの連携（任意）

タスク画面のGitHubの欄は、アプリの起動前に次の環境変数を設定した場合だけ表示する。未設定のときは「連携していません」と案内し、自分のタスクはそのまま使える。値はログ・画面・エラーへ出さない。

| 環境変数 | 内容 |
| --- | --- |
| `INUI_GITHUB_TOKEN` | GitHubのトークン。Issue・PRの読み取り権限だけを付ける（fine-grained tokenなら対象リポジトリのIssues・Pull requestsのRead-only） |

```sh
# 例: 現在のシェルだけで設定して起動する（履歴に値を残さないよう、read -s などで入力する）
read -rs INUI_GITHUB_TOKEN && export INUI_GITHUB_TOKEN
make app-dev
```

`make app-dev`・`app-smoke`は、この変数だけをアプリのプロセスへ渡し、推論サーバーには渡さない。`GH_TOKEN`・`GITHUB_TOKEN`は使わない。自分が担当のIssue・自分が作ったPR・レビューを依頼されたPRを読み取り、inuiからは更新しない。Backlogの連携は2026-11-18に削除したため、`INUI_BACKLOG_SPACE`・`INUI_BACKLOG_API_KEY`を設定していても使わない。

## タスクとMarkdownの確認

`自分のタスクを確認したい`でタスク画面、`Markdownを見やすく表示したい`でMarkdownの表示を開く。2つ目以降の用件は、右下のボタンから入力欄を開いて入力する。

1. タスク画面で`ADRの下書きを書く`を追加し、チェックを入れて完了にする。「看板」に切り替え、カードをドラッグするか「←」「→」で列（To do・Doing・Done）を移せることを確認する。GitHubの欄は参照のみで、看板には載らない。
2. 画面を開き直し、さらにCtrl+Cで停止して`make app-dev`で起動し直した後も、完了したタスクが残ることを確認する。
3. Markdownの表示で、このリポジトリの`docs/adr/0009-feature-packages-and-subject-change.md`などをドロップまたは選択し、目次・表・コードブロックが表示されることを確認する。Mermaidを含む文書（`docs/adr/`の一部やIssueの下書き）では図が描画される。

4. `絵を描きたい`でホワイトボードを開き、名前を入力して「作成」を押す。開いた直後はペンが選ばれているので、ドラッグで線を描ける。図形・文字はツールバーから選ぶ。「保存」を押すと保存され、別のボードを開いてから戻っても描いた内容が残ることを確認する。画像の書き出しは左上のメニューから行う。

自然言語の送信や画面の表示だけでは保存しない。Markdownのファイルはブラウザ内だけで読み、サーバーへ送らない。ホワイトボードのCSS・フォントはアプリが`/excalidraw/`から配信し、外部のCDNから読み込まない。

## 失敗・リセット・テスト

対象外機能・未対応操作・曖昧入力では、保存せず固定の案内を入力欄の上の履歴に表示する。推論の接続失敗、不正な応答、本文受信を含む25秒の期限超過は安全なエラーを表示し、入力し直すか「もう一度試す」で同じ文を送り直せる。上流の例外本文は表示しない。推論接続先はloopbackだけを許し、アプリのHostとPOSTのOriginも制限する。

初期状態へ戻すときはアプリをCtrl+Cで停止してから、次を実行する。

```sh
make app-reset
make app-dev
```

`app-reset`は`.local-poc/app.sqlite`の自分のタスクとホワイトボードを空に戻す。未適用のマイグレーションがあれば先に適用し（初めてなら表もここで作る）、マイグレーションの記録は残す。適用済みの記録があるのに表がないDB（壊れたファイルの一部だけを戻した場合など）では表を作り直さずに失敗するため、記録と表がそろったバックアップから戻す。GitHubのIssue・PR、`.local-jev`のモデル重みは変更しない。

型検査・ビルド・コア/API/SQLite/UI操作のテストは`make app-check`、コアの通信契約・失敗処理だけは`make core-check`で確認する。固定応答を注入したテストは実NLI精度の証拠にはしない。

`make lint`でアプリ・コア・検証スクリプトのlintとGitHub Actions定義の検証を行い、`make ci`でlintと`app-check`をまとめて実行する。新たに追加したBiome・actionlintを使うにはdevShellへ入り直す。CIではモデルを起動せず、保存済み応答の再照合と通信を注入したテストを使う。

`make app-model-check`はキャッシュ済みモデルを直接呼び、MVP.mdの20入力（画面11・案内9）を検証する。外部通信やHTTPを使わないため、HTTP経路とは別の記録になる。サーバー2つが起動したら、別のdevShellで`make app-probe`を実行すると、20入力を実際の受付APIへ送って分類を照合できる。タスク・ボードは保存しない。

起動からHTTP検証までを1コマンドで行う場合は、次を使う。検証が終わると、このコマンドが起動したサーバーを停止する。画面を使い続ける場合は`make app-dev`を使う。

```sh
nix develop --command make app-smoke
```

`app-smoke`も既存の正常なサービスは再利用する。別サービス・別モデル・接続権限エラーは上書きせず停止する。手動で分けて管理したい場合だけ、`make jev-local-serve`と`make app-run`を別ターミナルで使う。

2026-11-18、予定比較とBacklogの連携を削除した6候補で固定revisionの実Engine検証を行い、文書・タスク・ホワイトボードの20入力すべて（画面11/11件・案内9/9件）が一致した。入力は、予定比較の4件を外して予定の確認1件（`山田太郎さんと佐藤花子さんの予定を確認したい`）を加え、`Backlogの課題を見たい`をタスク画面から対象外の機能へ移した。候補説明は、タスクの説明から「Backlogの課題」を外し、対象外の機能の説明から「社員の予定比較」を外して、例に「社員の予定の確認」「Backlogの課題の確認」を加えた。ほかの説明は変えていない。同じ入力で比べた別案では、予定比較を外すだけだと予定の確認が曖昧入力に、例を「スケジュールや予定の確認」とすると「開いて」が対象外の機能に、曖昧入力の説明から「予定」を外すと「確認したい」「開いて」がそれぞれ別の候補に、タスクの説明からBacklogを外すだけだと「Backlogの課題を見たい」がタスク画面に分類された。「確認したい」（曖昧0.191・タスク0.189）と「開いて」（曖昧0.183・対象外の機能0.177）は1位と2位の差が小さく、確信度の低い入力の扱いは[Issue #27](https://github.com/abi-yusuke-wada/inui/issues/27)で検討する。検証用の20入力に含めていない入力では、`バックログの課題を見たい`（音声入力のカタカナ）と`Backlogのチケットを確認したい`は対象外の機能に分類された。予定比較を削除した時点の説明での確認では、`佐藤さんと鈴木さんの予定を見たい`・`明日のスケジュールを見たい`が、対象外の機能ではなく曖昧入力（再入力の案内）に僅差で分類された。どちらも画面は開かない。Engine直接呼び出しで平均約15.3秒・中央値12.0秒・最大36.3秒だった。予定比較の削除時の検証（平均約12.1秒・最大44.2秒）とともに、11-17の23入力（平均約5.8秒・最大9.4秒）より遅い。同じ開発機で他の処理が動いており（記録直後の負荷平均は4〜6）、時間は参考値とする。原因は確認していない。[保存応答](poc-nli-responses-2026-11-18.jsonl)は`make app-replay-check`で推論・通信なしに再検証できる。申請を題材にしていたときの[保存応答](poc-nli-responses-2026-11-10.jsonl)は履歴であり、現コアでは再生しない。これは新たなHTTP実測や実ブラウザの確認とは区別する。直近のEngine検証結果は`.local-poc/model-verification.json`、HTTPプローブ結果は`.local-poc/http-verification.json`へ保存する。

### バックエンドのログ

バックエンドは`src/logger.ts`を使い、起動・停止・API処理・初期化の結果を1行JSONで出力する。`debug`・`info`は標準出力、`warn`・`error`は標準エラーへ出す。既定の`info`ではAPIの完了と失敗を記録し、静的ファイルの成功も見る場合は次で起動する。

```sh
LOG_LEVEL=debug make app-dev
```

`LOG_LEVEL`は`debug`・`info`・`warn`・`error`だけを使い、未指定や不正値は`info`に戻す。起動管理からアプリへも検証したレベルだけを引き継ぐ。APIの成功は`info`、4xxは`warn`、5xxは`error`、静的配信の成功は`debug`で記録する。

各ログにはISO形式の`timestamp`、`level`、`event`、固定の日本語`message`を含める。要求完了時はサーバーが生成した`request_id`・`method`・固定の`route`・`http_status`・`elapsed_ms`、失敗時は固定の`error_code`も記録する。同じIDを応答の`X-Request-Id`へ返すため、ブラウザのNetworkと起動端末のログを照合できる。受信した同名ヘッダーをそのまま使わない。

入力文・人名・日付や金額・クエリ・任意URL・Host・認証ヘッダー・例外本文やstackは記録しない。未知の経路は`other`とし、許可した項目と値だけを出力する。ログ出力に失敗してもAPIの成功応答を失敗へ変えない。

自然言語での画面選択に失敗した場合は、アプリの起動端末の`intent_request`行で`http_status`・`elapsed_ms`・`error_code`を確認する。504で約25000msかつ`timeout`ならコアの推論期限超過で、画面も時間超過の案内を表示する。503なら推論への接続や利用可能状態、502なら応答契約の確認が必要になる。タスク・ボードの保存や連携先の取得などの結果は`http_request`で追える。タスクのIDを含む経路は`/api/tasks/local/:id`、画面のチャンクは`/assets/*`として記録する。

起動直後の判定の時間: 起動直後の初回だけ画面の判定が時間切れになり、2回目は成功するとの利用者報告があった（申請・予定比較を題材にしていたときと、2026-11-19にホワイトボードを開いたとき）。local-jevは起動時にwarm-upを行うが、短い英語の問いだけで、inuiと同じ形（日本語の入力と6候補）の判定は事前に行わない。

2026-11-19、`make app-dev`と同じ条件で推論サーバーを3回起動し直し、判定を6件ずつ測った（すべて期待どおりに分類）。モデルのファイルがOSのキャッシュにないときは、準備完了まで21〜29秒、最初の判定が9.0〜9.4秒で、2件目以降（4.4〜5.5秒）の約2倍だった。キャッシュにあるときは、準備完了まで7.6秒、最初の判定も4.4秒だった。3分間使わずに置いた後も5.5秒で、遅くはならなかった。判定の時間は、開く画面（ホワイトボード・Markdown・タスク）によって変わらない。一方、PCが混んでいたとき（2026-11-18、他のCLIのセッションが複数動き、スワップを3GB以上使用）は、Engineの直接呼び出しでも最初の判定が36秒、続く数件も21〜25秒だった。起動直後の上乗せと、PCの混み具合が重なると、コアの25秒の期限を超えることがあると考えられる（利用者の環境で時間切れになったときのログは取得していない）。

このため`make app-dev`・`make app-smoke`は、推論サーバーを起動した場合だけ、URLを案内する前に判定を1回行う（起動済みの推論サーバーを再利用する場合は行わない）。2026-11-19の`make app-smoke`では、準備の判定に10秒かかり、その後のHTTP経路の20件は平均7.3秒だった。ただし最大の20.2秒は、同じ開発機で別の処理（Mermaidの画像生成）が動き、負荷平均が8.95まで上がった時点の1件で、準備の判定をしても混み具合による遅れは防げない。準備の判定に失敗しても起動は続け、最初の判定に時間がかかる場合があることを表示する。25秒の期限は変えず、正式な30秒条件の測定はIssue #15で行う。時間切れが起きた場合は、起動端末の`intent_request`の行が`http_status: 504`・`elapsed_ms`が約25000・`error_code: timeout`になる。画面の「もう一度試す」で再試行できる。

ブラウザが白画面のまま読み込みを続ける場合は、起動中のターミナルを残し、別のdevShellで`make app-web-diagnose`を実行する。`/`・`/legacy`・JavaScript・CSSを本文受信まで各3秒以内で確認し、配信内容と現在のビルドの一致を`.local-poc/web-check.json`へ保存する。HTTPステータス、期限超過、形式・内容の不一致を区別し、本文は出力しない。推論やタスクの保存は呼ばない。業務画面のチャンク（`/assets/`）は対象外。この診断が成功してもブラウザだけが表示されない場合は、開いたURLとブラウザのConsoleのエラーを確認する。

`make app-ui-check`はUI操作に加え、生成したHTML・production bundle・CSSによる初期描画と、参照するチャンクがすべて出力されていることもJSDOMで確認する。初期画面は推論やAPIを待たずに表示する。JSDOMでの確認は実HTTP配信や実ブラウザの成功とは分けて扱う。

## ローカルで確認できる範囲

これは単一の検証利用者向けのローカルPoCで、Turso・OAuth・AWSへの配置は未実装。SQLiteの再起動後の保持を、Tursoや新しいLambda実行環境での永続化確認として扱わない。公開クラウド資源は作らず、部署向けにそのまま公開しない。

モデルの部署向け配置、Lambdaでの起動・RSS・費用、ブラウザからの正式30秒測定（Issue #15）、音声入力と旧形式との評価は残る。ローカルで画面を開けたことや、コアの25秒期限だけでこれらを完了したとは扱わない。
