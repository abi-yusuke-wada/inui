# ADR-0010: DBの接続とマイグレーションを共通の部品にまとめる

- 状態: 決定（2026-11-18、利用者の回答による）。範囲はDBの土台（共通の接続・非同期のSQL実行・番号付きのマイグレーション・リセット）までとし、Turso Cloudへの実際の接続（クライアントの選定・依存の追加）は含めない。
- 関連: [Issue #13](https://github.com/abi-yusuke-wada/inui/issues/13)、[ADR-0001](0001-mvp-hosting-and-storage.md)、[ADR-0009](0009-feature-packages-and-subject-change.md)、[実行手順](../poc-local.md)

## 背景

- [ADR-0001](0001-mvp-hosting-and-storage.md)で、部署展開時のDBにTurso Cloudを採用した。エンジン・接続クライアント・テーブル定義・マイグレーションは、Issue #13で決めることになっている。
- [ADR-0009](0009-feature-packages-and-subject-change.md)で業務機能をパッケージに分けた。タスク（`local_tasks`）とホワイトボード（`whiteboards`）の保存処理は、それぞれが`.local-poc/app.sqlite`へ別々に接続し、起動のたびに`CREATE TABLE IF NOT EXISTS`で表を作っていた。表の変更（看板の列の追加）は、タスクの保存処理の中で個別に行っていた。
- この形では、表を変えるたびに機能ごとの移行処理が増え、どの変更を適用したかの記録も残らない。node:sqliteの同期APIに依存しているため、HTTPSで接続するTursoへ切り替えるときに、保存処理とAPIの呼び出し側をすべて書き直す必要があった。
- 画面はモックアップで並行して決めている。保存する項目が変わっても表を安全に変えられるよう、先にDBの土台を用意する。

## 決定

- 共通の部品は`packages/features/kit`の`db`（`@inui/feature-kit/db`）に置く。業務機能は`Database`（`query`・`run`・`batch`・`close`）だけを使い、node:sqliteを直接使わない。
- 操作はすべて非同期にする。複数の文をまとめて確定する方法は`batch`（1つのトランザクション）だけにし、途中で応答を待ちながら進めるトランザクションは持たない。HTTPS接続では、まとめて送れば1往復で済むため。
- 1回に渡すSQLは1文だけにする。node:sqliteは2つ目以降の文を黙って捨てるため、ローカルの実装は残りがあれば失敗させる。読み取った整数は、安全な範囲なら`number`、超えるものは`bigint`で返す。
- ローカルの実装（`openLocalDatabase`）はNode標準の`node:sqlite`で、従来どおり`.local-poc/app.sqlite`を使う。DBを置くディレクトリを新しく作るときは、所有者だけが開けるようにする（0700）。node:sqliteは同期APIで、ロックを待つ間はサーバー全体（`/api/health`を含む）が止まるため、別の接続が書き込み中なら待たずに失敗させる（以前と同じ）。待ちながら他の要求に応えるには接続を別スレッドへ移す必要があり、ローカルの1人用のMVPには見合わないため行わない。
- アプリは起動時に接続を1つだけ開き、タスクとボードの保存処理で共有し、停止時に閉じる。
- マイグレーションは機能ごとに持つ（`taskMigrations`・`boardMigrations`）。入口の`src/db.ts`が一覧にまとめ、起動時と`make app-reset`の前に、未適用のものだけを適用する。適用済みのidは`schema_migrations`表に記録する。
  - 1件ずつ、1つのトランザクションで適用する。失敗したら表の変更も記録も残さず、後続も適用しない。
  - 記録の追加をトランザクションの先頭に置く。別のプロセスが同じマイグレーションを先に適用していた場合は、記録の重複で全体を取り消し、適用済みとして扱う。`up`が失敗した場合も、先に適用されていないかを確かめてから失敗にする。
  - 一度適用したidの内容は変えない。表を変えるときは、新しいidのマイグレーションを足す。
  - マイグレーションの仕組みより前に作られた表は、そのまま引き継ぐ。看板の列がないタスクの表には、以前の保存処理と同じく列を加え、未完了をtodo、完了をdoneにする。
- 表の形は変えない。`local_tasks`の`done`列も、互換のため残す。ボードの更新は、読み込みと書き込みの間に別の更新が入らないよう、1つの文（`UPDATE ... RETURNING`）にした。
- DBを開けない場合やマイグレーションに失敗した場合は、例外の本文を出さず、固定のコード`db_setup_failed`を記録して起動を中止する。マイグレーションを適用したときは`db_migrated`を記録する。
- 旧題材の`applications`・`metadata`表は読み書きせず、削除もしない。

## 影響と未決事項

- 保存処理（`TaskStore`・`BoardStore`）と、それを呼ぶAPIが非同期になった。保存処理はDBを受け取って使うだけで、接続を開閉しない。
- 既存の`.local-poc/app.sqlite`（申請の題材で作ったものと、ADR-0009の実装で作ったもの）の複製に適用し、既存の表と件数が変わらないこと、2回目は何も適用しないことを確認した。
- Turso Cloudへの接続は未実装・未検証。次の作業で、クライアントの候補（`@libsql/client`、`@tursodatabase/serverless`、HTTP APIを直接呼ぶ実装）を、依存の大きさ・ローカルとの差・SQLの互換（STRICT表・`json_valid`・`RETURNING`）で比べて決める。接続先のURLとトークンは環境変数で与え、ログ・応答に含めない。
- 部署展開時にマイグレーションをいつ・どこから適用するか（Lambdaの起動時には適用せず、デプロイの手順で適用する等）は、Issue #14で決める。
- 利用者ごとのデータの分離は、#12で認証を決めるときに、利用者の列を加えるマイグレーションとして行う。
- 業務機能を外すときは、`src/db.ts`の一覧から外す。作られた表とデータは残る。
