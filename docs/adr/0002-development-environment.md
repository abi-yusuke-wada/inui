# ADR-0002: 開発環境をNix Flakesとdirenvで管理する

- 状態: 決定（2026-10-30）
- 更新: 2026-11-02、Codexの機密ファイル拒否を追加。
- 更新: 2026-11-06、GitHubのIssue・PR操作を限定MCPへ分離する判断を[ADR-0007](0007-limited-github-mcp.md)に記録。
- 関連: [Issue #3](https://github.com/abi-yusuke-wada/inui/issues/3)、[ADR-0001](0001-mvp-hosting-and-storage.md)

## 背景

ADR-0001で、フロントエンドはReact + TypeScript、APIはTypeScript + Hono / AWS Lambdaを採用した。開発者ごとの差異を減らし、MVPの開発・検証を再現できる環境が必要になった。

また、開発支援CLIのサンドボックスで秘密情報（`.env`・`.env.*`、`.aws` 配下）の読み取りを拒否する必要がある。Codexの従来の `workspace-write` は書き込み範囲の制限であり、機密情報の読み取りを防げないため、読み取り拒否を設定する権限プロファイルへ移行する。Linux・WSLでサンドボックスを動かすには `bubblewrap` と `socat` が必要になる。

## 比較した案

| 案 | 評価 |
| --- | --- |
| Nix Flakes + direnv | ツールとバージョンを `flake.lock` で固定でき、ディレクトリへの移動だけで環境に入れる。Nixとdirenvの導入が必要 |
| Nix Flakesのみ（`nix develop` を手動実行） | 構成は最小だが、環境に入り忘れるとサンドボックスが起動できない |
| 各自でNode.js等を導入（nvm・Volta等） | 導入は手軽だが、バージョンやサンドボックス用ツールの差異を防げない |

いずれもOSSで、ライセンス費用・クラウド費用は発生しない。

## 決定

- Nix Flakes（nixpkgs `nixos-26.05`）でdevShellを定義し、direnvの `use flake` でディレクトリ移動時に自動で読み込む。
- devShellには必要最小限として次を含める。
  - Node.js 24 LTS（`nodejs_24`）
  - pnpm（パッケージマネージャー）
  - `bubblewrap`・`socat`（Linux・WSLのみ。CLIのサンドボックス実行用）
- サンドボックスが利用できない場合は起動を止める設定とし、保護なしで実行しない。
- ビルド・実行・テスト等のコマンドは `Makefile` に集約する。pnpmのscriptsだけに置く案と比べ、Nixの検証やサンドボックスの確認などNode.js以外のコマンドも同じ入口から実行でき、READMEや開発支援CLIへの案内を `make <ターゲット>` に統一できる。GNU MakeはdevShell（`mkShell` の標準環境）に含まれ、追加費用はない。

## 影響

- 開発者はNixとdirenvを導入し、初回に `direnv allow` を実行する。CLIはdevShellに入った状態で起動する。
- Lambdaで使うNode.jsランタイムとのバージョン整合は、Issue #4の構築時に確認する。
- 社内でmacOSを使って開発する人はいないため、macOS（`aarch64-darwin`・`x86_64-darwin`）は `nix flake check --all-systems` で定義を評価できることだけを確認し、実機での動作確認はしない。nixpkgs 26.05は `x86_64-darwin` をサポートする最後のリリースである。
- テスト・Lint等のツールやディレクトリ構成は、Issue #4の実装に合わせて追加する。

## 機密ファイルのアクセス制御（2026-11-02追加）

Codexの [プロジェクト設定](../../.codex/config.toml) では、既定のプロファイルを読み取り専用の `inui-readonly`（`:read-only` を継承）とし、実装時だけセッション内の `/permissions` で `inui-dev`（`:workspace` を継承）に切り替える（下記「AI開発エージェントの権限・責務分離」）。当初は `:workspace` を継承する `inui` の1プロファイルだった。`inui-dev` では通常の作業領域の編集と `approval_policy = "on-request"` を維持し、`.git`・`.agents`・`.codex` 等の標準保護を引き継ぐ。作業領域外への書き込み権限は追加しない。

拒否対象は、既存の [共有設定](../../.claude/settings.json) に合わせたプロジェクト内とホーム配下の `.env`・`.env.*`、プロジェクトの `.aws` と `~/.aws`。`.aws` はglobではなくディレクトリそのものを拒否し、起動後に作成されたファイルも保護する。ただし、起動時に存在しないディレクトリは拒否されないため、`flake.nix` の `shellHook` で作業領域の `.aws` と `~/.aws` を事前に作成する（権限700、既存の場合は変更しない）。`shellHook` はdirenvと `nix develop` のどちらで開発環境に入っても実行される。ローカル設定のGit操作の拒否ルールとは分け、ファイルアクセスをOSのサンドボックスで拒否する。AGENTS.mdへの指示や `.gitignore` だけでは読み取りを強制できないため、この方式を選ぶ。追加の依存関係・クラウド資源・利用料は発生せず、CLIごとの設定の保守と検証が必要になる。

旧 `sandbox_mode` はプロジェクト設定から削除する。権限プロファイルと旧 `sandbox_mode`・`sandbox_workspace_write` は併用できず、他の設定階層や起動引数に旧設定があるとプロファイルが適用されない場合がある。グローバル設定は変更しない。信頼済みのプロジェクトでCodexを再起動し、プロファイルを有効にする。[OpenAI公式の権限設定](https://learn.chatgpt.com/docs/permissions)

Linux・WSLの再帰globは `glob_scan_max_depth = 8` とし、各サンドボックスプロセスの起動時に一致するファイルを列挙する。深さ8を超える配置や、起動済みのプロセスの途中で作成された新しい一致ファイルまで保護するとは扱わない（ディレクトリ単位で拒否する `.aws` を除く）。必要な配置には明示的なパスを追加し、新しいプロセスで再確認する。`.env.example` も `.env.*` に一致するため拒否対象となる。

2026-11-02、利用者の明示的な判断により、走査深さ8を維持する。Codexが対象とする作業領域・ホーム配下では、再帰globの走査深さ8を超える場所に機密情報を含む `.env`・`.env.*` を置かないことを運用前提とする。この前提の下で、深い配置が自動的に保護されない制約を受容し、追加の全階層走査や配置検出・起動停止の仕組みは今回のMVPには導入しない。深い配置が必要になった場合は、使用前に拒否設定と運用前提を再検討する。

ホーム起点の `~/**/.env`・`~/**/.env.*` は、走査中に読み取れないディレクトリ等でエラーが起きるとサンドボックスを構築できず、コマンドを起動できない。保護範囲を狭めるより、起動できない側（保護なしで実行しない側）に倒れる挙動を受け入れ、ホーム全体の保護を維持する。起動できない場合は、エラーになったディレクトリの権限を確認する。

`:workspace` はファイルシステム全体の読み取りを許可するため、作業領域内に外部ディレクトリを指すシンボリックリンクがあると、リンク先の `.env` はglobの展開対象にならず読み取れる（2026-11-02に `codex sandbox` で確認）。作業領域外の読み取りを禁止するプロファイルは、Nixストア等の開発ツールの読み取りも妨げるため採用しない。代わりに、作業領域外を指すシンボリックリンクを作らないこととし、`make sandbox-check` で検出する（`.git`・`.direnv`・`node_modules` を除く）。

`make sandbox-check` は実行した時点のリンクだけを検査するため、エージェントが実行中に作業領域外を指すリンクを作ると検出できない。CLIの設定には、リンクの作成やリンク先の読み取りを一般的に拒否する手段がない。ホーム配下の `.env` はリンク先の実体も `~/**/.env` の拒否対象となるため、この経路で読み取れるのは、作業領域とホームの外（`/tmp`、WSLの `/mnt/c` 等）にある `.env` に限られる（このリンク先の挙動は未検証）。この残存リスクを受け入れ、作業領域とホームの外に機密情報を含む `.env` を置かないことを運用前提とする。調査の段階は読み取り専用のため、リンクを作れない。

以下は、当初の `inui` プロファイル（`:workspace` を継承）を既定としていた時点で、Codex CLI 0.165.0 / LinuxのNix環境からプロファイルの強制指定をせずに `codex sandbox -- ...` を実行した検証の記録である。現行の `inui-readonly`・`inui-dev` での同等の検証は未実施で、状況は [AI開発エージェントの権限と運用](../agent-security.md) に記録する。プロジェクト内・入れ子・ホーム配下のプロジェクト外のダミー `.env`、プロジェクトとホームの `.aws` 内のダミー、作業領域内を参照先とするシンボリックリンク経由（作業領域外を参照先とするリンクは前述のとおり読み取れるため対象外）について、Pythonの読み取り・`cat`・書き込みが拒否された。通常ファイルの読み書きと作業領域外の書き込み拒否も確認した。実際の機密情報は使用せず、作成した一時ファイルは削除済み。macOS・Windowsと、外部MCPツール等の別の実行経路は未検証とする。

## GitHubへの通信と認証情報（2026-11-02追加・同日改定）

以下は2026-11-02時点の判断である。2026-11-06、CodexのIssue・PR操作には専用PATと操作別承認を使う限定MCPを追加することにした（[ADR-0007](0007-limited-github-mcp.md)）。コマンドの通信制限と認証情報の読み取り拒否は維持し、コードのpushはこのMCPの対象に含めない。

当初、Codexの実行環境からGitHub CLI・Gitで情報を取得できなかったため、`features.network_proxy` と `permissions.inui.network` で `github.com`・`api.github.com` への通信を許可した。再起動後にGitHub CLI・Gitの取得が成功し、許可外の `example.com` が拒否されることを確認した。

しかし、`:workspace` はファイルシステム全体の読み取りを許可するため、外部のIssue等に含まれる悪意ある指示により、GitHubのトークン（`~/.config/gh`）を読み取って許可済みのGitHubへ送る経路ができる。攻撃者が自身のトークンを指示に含めれば、`github.com` への通信だけで作業領域の内容を持ち出すこともできる。利用者の判断により、最も安全な構成を採用し、通信許可を取り消した。

| 案 | 防げること | できなくなる作業 |
| --- | --- | --- |
| 認証情報の一部を拒否し、GitHubへの通信を許可する（当初案） | GitHubのトークン以外の認証情報の読み取り | なし。トークンの読み取りと送信の経路が残る |
| 読み取り専用のトークンをCodexに渡す | トークンを使った書き込み | Codexからの返信・push。攻撃者のトークンを使った持ち出しは残る |
| Codexの通信を無効にし、Claudeは `gh`・`git push` を毎回の承認でサンドボックス外で実行する（採用） | トークンの読み取りと、承認していない送信 | CodexはGitHubの情報を取得できない。ClaudeのGitHub操作は毎回の承認が必要になる |

決定内容は次のとおり。追加の費用はなく、承認の手間が増える。

- Codex: 通信の許可を削除し、ネットワーク無効の既定値に戻す。GitHubのトークンを含む `~/.config/gh` と、作業に不要な認証情報（`~/.ssh`・`~/.gnupg`・`~/.netrc`・`~/.git-credentials`、各CLIの認証ファイル `~/.claude/.credentials.json`・`~/.codex/auth.json`）の読み取りを拒否する。`codex sandbox` で、存在する対象の読み取りと `api.github.com` への通信が拒否され、通常ファイルは読めることを確認した（内容は出力していない）。
- Codex: コマンドに渡す環境変数を `shell_environment_policy.inherit = "core"` で基本的なもの（PATH・HOME等）に限定する。Codex CLI 0.165.0の既定は全環境変数の継承で、名前に `TOKEN` を含む変数も除外されないため、`GH_TOKEN` 等を環境変数で与えると、ファイルの拒否や通信の無効化では防げず、コマンドの出力からモデルに渡り得る。2026-11-02、利用者のシェルで `GH_TOKEN=dummy-inui codex` として起動し、`inui-readonly` のコマンド内で `GH_TOKEN` が未設定になることを確認した。
- Claude: 共有設定で `~/.config/gh` の読み取り・編集を拒否する。`gh` と `git push` はトークンを使うため、サンドボックスの対象外（`excludedCommands`）として実行し、`ask` で毎回利用者の承認を求める。個人設定の確認なしの許可は削除する。
- PRへの返信・レビュー依頼等のGitHub操作はClaudeが担当し、Codexは使わない。
- GitHubのトークンは、このリポジトリだけを対象とする権限の狭いトークンに置き換えることを推奨する。

## AI開発エージェントの権限・責務分離（2026-11-02追加）

外部のIssue・PR・コメントに含まれる悪意ある指示による実行・認証情報へのアクセス・GitHubの不正操作を抑えるため、作業を「調査（読み取り専用）」「実装・テスト（作業領域への書き込み）」「GitHubへの反映（承認付きの書き込み）」の3段階に分け、段階ごとの権限で起動する。

| 案 | 評価 |
| --- | --- |
| 1つの権限で常に書き込み可能にする | 手軽だが、調査中に読んだ外部の指示がそのまま書き込み・実行につながる |
| 段階ごとに権限を分け、既定を読み取り専用にする（採用） | 調査中の変更を防げる。実装時に起動し直す手間が増える |

- Codexは既定のプロファイルを読み取り専用の `inui-readonly` とし、実装時だけ `inui-dev` を指定する。旧 `sandbox_mode` は権限プロファイルと併用できないため使わない。
- Claude Codeは既定のモードを `default` とし、ファイル操作ツールによる作業領域外への書き込み、claude.aiのコネクタ、マージ等のGitHub操作を拒否する。
- 両CLIで、SSH鍵・GnuPG・レジストリやCLI自身の認証ファイルも読み取り拒否の対象に加える。
- AIによるマージの技術的な禁止は、反映用の認証主体を分離したうえでGitHubのRulesetで行う。CLI側の拒否ルールは補助とする。

追加の費用はない。起動方法・検証結果・GitHub側の設定案・残るリスクは [AI開発エージェントの権限と運用](../agent-security.md) にまとめる。
