# ADR-0008: 4つの業務をローカルPoCで実装する

- 状態: 決定（2026-11-10）。ローカル開発・検証の構成を決める。部署展開の構成・費用は未決定。
- 関連: [Issue #4](https://github.com/abi-yusuke-wada/inui/issues/4)、[MVP](../../MVP.md)、[ADR-0001](0001-mvp-hosting-and-storage.md)、[ADR-0003](0003-separate-core-from-poc-app.md)、[ADR-0006](0006-local-model-for-mvp.md)、[実行手順](../poc-local.md)

## 背景

休暇申請・交通費精算・申請状況の確認に、複数人の予定比較を加える。画面と業務データを自前で用意し、自然言語で画面を開く方法とメニューから開く旧形式を、同じAPI・UI部品・データで比較する。

利用者には既存の常駐サーバーがない。まず開発機で実NLIを含む経路と業務操作を確認する。ローカルで動作することと、モデルを含むAWS配置の成立を区別する。公開クラウド資源は今回作らない。

## 比較した案と費用

| 案 | 費用・作業負担 | 判断 |
| --- | --- | --- |
| 開発機でNode・SQLiteファイル・ローカルNLIを動かす | 公開クラウドや公式JevのAPI利用を必要としない。モデル取得、ディスク・CPU・メモリ、プロセスの起動・停止は必要 | 採用。業務と画面の検証を先に進められる |
| AWS・Turso・OAuthと推論配置を先に構築する | 配置検証、認証設定、クラウド資源・運用の負担が先行する。既存の常駐先もない | 今回は実装しない。部署展開時の判断・検証として残す |
| 推論を固定応答へ置き換えて製品の判定に使う | 推論資源を省けるが、実NLIで振り分ける研究目的を検証できない | 不採用。固定応答は通信・境界の単体テストに限る |

料金の推定額は置かない。開発機での起動を、運用費用や資源負担がないこととは扱わない。

## 決定

- アプリはルートパッケージの`src/`、Intent判定のコアは`packages/core/`に置き、依存はアプリからコアへの一方向とする。2026-11-11の利用者の指示を受け、単一アプリのための`apps/poc`という階層を取り除いた。コアは業務アプリ・DB・Reactに依存しない。
- テストは実装の隣へ置く案と分離する案を比較し、同日の利用者の指示により`tests/`へ分ける。ルートのアプリ・画面・実行スクリプトのテストは`tests/`、独立したコアのテストは`packages/core/tests/`へまとめる。配置をたどりやすくし、型検査・lintの対象に含めながら製品ビルドから除外する。追加の依存・費用は発生しない。
- コアは`nli-deberta-large`を固定し、4画面のIntentと対象外機能・未対応操作・曖昧入力の計7候補を検証する。wire候補`unspecified_application`は検証後に内部の`clarify`へ対応付ける。未知のIntent・Tool・UI・args、固定モデルと異なる応答、不正な確率・使用量は拒否する。
- アプリはHono・Reactを使い、申請をNode標準の`node:sqlite`でローカルファイルへ保存する。TypeScriptによる型検査、esbuildによるビルド、Node標準テストとjsdomによるUI操作テストを採用し、コマンドはMakefileへ集約する。
- バックエンドのログは`src/logger.ts`へ集約し、標準機能で時刻・レベル・固定イベントと許可したメタデータだけを1行JSONへ整える。各所の`console`直書きは形式や記録範囲が揺れるため、共通化する。外部のログ基盤や専用ライブラリを先に導入する案は、現段階の少数のイベントには追加設定・依存・運用の負担が先行するため採用しない。追加の依存・利用料はなく、収集先の運用や保存費用は部署展開時に検討する。
- APIは要求ごとにサーバー生成のIDを発行し、応答ヘッダーと完了ログで共有する。成功APIは`info`、4xxは`warn`、5xxは`error`、静的配信の成功は`debug`とする。既定は`info`、`LOG_LEVEL`の既知の4値だけを使う。入力・人名・申請内容・任意URL・クエリ・認証ヘッダー・例外本文を記録せず、出力障害でも業務応答を変更しない。
- Node・pnpmはNixから提供し、プロジェクト固有のコンパイラ・バンドラー・ライブラリは直接バージョンとlockfileで固定する。devShellはプロジェクトのCLIをPATH末尾へ追加し、ビルドはローカルの実体を明示して呼ぶ。依存取得は利用者の認証設定から分離し、インストールscript・検証コマンドからの自動installは使わない。
- ローカルHTTPサーバーはIPv4のloopbackで待ち受ける。2026-11-11の利用者の指示を受け、アプリの既定ポートを`127.0.0.1:8766`へ変更した。通常の起動・診断はこのポートを使い、3000番を自動起動しない。検証用の`INUI_POC_PORT`では1024〜65535の整数を指定できる。Hostは選択したポートの`127.0.0.1`と`localhost`だけに限定し、POSTでは同一OriginとJSON、本文16KiB以下を要求する。これはローカルPoCの制限であり、部署向けの認証・認可を実装したことにはしない。
- `make app-dev`でアプリと実NLIをまとめて起動し、`make app-smoke`で起動からHTTP検証までを行う。既存の正常なサービスは再利用し、終了時は自分で起動したプロセス群だけを停止する。子プロセスへは実行に必要な環境変数だけを渡す。
- ブラウザは推論を直接呼ばず、サーバー側のコアがloopbackの`http://127.0.0.1:8765/v1/systemone`を呼ぶ。APIキー・公式サービスへの切り替えは使わない。リダイレクトを拒否し、JSON本文の受信まで25秒の期限を設け、安全な固定エラーへ変換する。
- 日付・金額・区分・状態は画面で明示操作する。自然言語から申請内容を保存せず、フォームの確定POSTだけで追加する。
- 予定比較の人名はサンプル社員辞書へ照合する。全名を優先し、一意な姓は選択済みにする。同姓と未知名は自動確定せず、画面で確認・選択する。LLMは使わない。
- 予定は参照のみとし、登録・削除は対象外とする。予定日の初期値は`2026-11-02`で、文章中の日付は抽出しない。`2026-11-02`・`2026-11-03`のサンプルを用意し、日付は画面で変更する。

## 影響と残る検証

アプリを複数並べる予定がない現段階では、ルートの`src/`へまとめる方が配置を追いやすい。別案の`apps/web`への改名は階層が残るため採用せず、ルートとコアの2パッケージに整理した。既存の依存の版は変えず、追加の取得費用は発生しない。アプリのビルド先はルートの`dist/`とし、SQLiteは従来と同じ`.local-poc/app.sqlite`を使う。

2026-11-11のWindowsからの表示確認では、WSL内のアプリはHTTP 200なのにWindowsの3000番は受信0byteでタイムアウトした。一方、8765番の推論サーバーはWindowsからHTTP応答と案内JSONを取得できたため、WSL全体の接続障害とは確定できない。グローバルなWSL設定変更は行わず、アプリのポートを8766へ切り替え、準備完了後に利用者からWindowsブラウザでの画面表示成功の報告を得た。追加のサービス・依存・公開インターフェースを増やさずに表示の問題を回避できた。3000番の根本原因と、実ブラウザでの業務操作は未確認。

ローカルSQLiteでの保存・再起動後の再取得は、Turso Cloud接続や新しいLambda実行環境からの読み取りを完了した証拠にはしない。Turso・OAuth・AWSへの配布、モデルの配置先は未実装・未確定であり、[ADR-0001](0001-mvp-hosting-and-storage.md)の部署展開方針を今回のローカル構成で置き換えない。Lambdaでのモデル起動・RSS・費用も未検証とする。

既存13入力の実測は3機能・6候補の履歴として保持する。予定比較を加えた7候補は、既存13入力に予定比較・未対応操作の6入力を加えて実NLIを検証した。最初は会議登録が曖昧入力となり18/19件だった。未対応操作の説明に会議登録を明示し、モデル・重み・入力・期待値を変えずに19/19件（正常13/13・対象外と曖昧6/6、人名選択4/4）の一致を確認した。[保存応答](../poc-nli-responses-2026-11-10.jsonl)は`make app-replay-check`で現コアへ再照合できる。

この実測はCPU・float32・4threads、固定revision・既存較正値でのEngine直接呼び出しであり、HTTPルートは実行していない。モデル初期化は約13.9秒、分類は平均約13.0秒・最大約22.0秒、PythonプロセスのピークRSSは3,039,952KiBだった。これは実行時の参考値であり、Lambdaの起動時間・必要メモリ・費用やブラウザ経路の保証には使わない。固定19入力を使って説明を調整した結果であり、日本語全般の精度を保証しない。

2026-11-11、利用者ホストの`make app-smoke`でも[HTTP19/19件・人名4/4件の一致](../poc-http-results-2026-11-11.json)を確認した。測定したのは当時の既定ポート3000で、現在の既定ポート8766での実測ではない。平均約8267ms・最大12713msで、測定範囲はIntent受付のみ。起動ログのモデル読込・warm-upは37.8秒だった。ブラウザ描画・保存・音声入力・Issue #15の正式条件は含めず、HTTP応答からruntimeや重みrevisionを観測したことにはしない。

Issue #4では本実装・ローカル動作と配置の検討を進める。Issue #15の正式な30秒条件は、採用する実モデルを含むブラウザ送信から最終結果の受信までを別途実測する。25秒のコア期限や分離した分類時間だけでは、正式条件を満たしたことにはならない。
