# ADR-0006: 正式MVPにローカル実NLIモデルを使う

- 状態: 決定（2026-11-06）。正式MVPはローカル実NLIを使い、`nli-deberta-large`を基準モデルとする。分類の合格基準は正常9件・対象外と曖昧入力4件の全件一致。公式Jev・自然言語からの自動補完・MCPは部署展開と費用承認の後へ延期する。推論配置はIssue #4で具体化する。
- 関連: [Issue #16](https://github.com/abi-yusuke-wada/inui/issues/16)、[Issue #4](https://github.com/abi-yusuke-wada/inui/issues/4)、[Issue #15](https://github.com/abi-yusuke-wada/inui/issues/15)、[ADR-0001](0001-mvp-hosting-and-storage.md)、[ADR-0003](0003-separate-core-from-poc-app.md)、[ADR-0004](0004-jev-first-intent-routing.md)、[ADR-0005](0005-local-jev-for-development.md)、[MVP](../../MVP.md)

## 背景

公式Jevの利用費用について社内承認が確定していない。承認・契約を正式MVP着手の前提にせず、ローカルの実NLIモデルを使ってMVPを先行させる方針へ変更する。公式Jevの契約と接続検証は、MVPの部署展開と費用承認の後へ延期する。

[ADR-0005](0005-local-jev-for-development.md)ではローカルモデルを開発時の例外とし、正式MVPには公式Jevを使うとしていた。この方針を変更し、モデル・分類基準・延期範囲を以下のとおり決定する。申請画面の選択までを実NLIで確かめることに範囲を絞り、自然言語から値を補完する処理とMCPの実装・検証は後へ分ける。

## 比較した案

| 案 | 費用・負担 | 評価 |
| --- | --- | --- |
| A. 公式Jevの承認・契約を待って正式MVPを進める | 公式APIの利用料と社内承認が必要。承認前は利用を前提にできない | 承認時期が未確定のため、MVPを先行させる利用者の方針に合わない |
| B. ローカル実NLIモデルで正式MVPを先行する（採用） | 公式APIの利用料は不要。モデルの取得、CPU・メモリ、推論プロセスの配置・稼働管理と運用の負担がある | 基準モデルと分類基準を固定し、実推論を使ってMVPを進める。推論配置はIssue #4で具体化する |
| C. 固定応答mockでMVPを先行する | 実モデルの推論負荷は不要 | 入力に応じた実推論を使う利用者の方針を満たさないため不採用 |

推論の配置と必要容量が未確定のため、料金や運用費の推定額はここでは置かない。ローカルモデルの利用を、配置・運用の費用がかからないこととは扱わない。

## 決定

- 正式MVPではローカルの実NLIモデルを使い、`nli-deberta-large`を基準にする。モデルを変更する必要が出た場合は利用者と相談し、独断では切り替えない。
- 分類の合格基準は、固定した正常9入力で9/9件、対象外・曖昧な4入力で4/4件、期待するIntentと一致することとする。正常系・異常系を別に集計する。
- MVPでNLIが担う範囲は、Intentから休暇申請フォーム・経費精算フォーム・申請一覧の3画面を選ぶところまでとする。日付・金額・区分・状態の自然言語からの抽出・自動補完は延期する。フォームの入力・値の選択、一覧の状態による絞り込みは、画面上の明示操作で行う。
- 公式Jevの契約・接続検証、自動補完、MCPの実装・接続検証は、MVPの部署展開と社内の費用承認の後へ延期する。
- LLM不使用を維持する。判断結果は引き続きホスト側でIntent・Tool・UI・引数の許可リストと照合して検証する。AIに業務APIや保存を直接実行させない。
- 本実装はIssue #4、正式な応答30秒以内の実測はIssue #15の責任とする。Issue #15では、実際のMVPに採用したローカルモデルを含む経路で計測する。
- 既存の「正常系と異常系でそれぞれ1件以上一致」という結果は、ローカル導入確認を終えた履歴として残す。今回の分類基準の達成や正式MVPの合格を示す記録にはしない。

## Issue #16の改定ゴールと現在の状態

Issue #16では、基準モデルを固定したうえで候補説明・出力仕様・失敗時の扱いと再現手順を整え、固定13入力の全件一致を実測で示す。公式Jevへの接続、自動補完、MCPの検証は今回のゴールに含めない。

- 基準モデル、候補説明、入力、期待するIntent、出力の仕様、ホスト側で拒否する不正な応答と通信失敗等の扱いを記録する。
- 実測では各入力のprovider・model・実際の結果・成否を記録し、正常9件と対象外・曖昧4件を別に集計する。
- 実行環境・手順・設定と検証結果をIssue #4へ渡し、本実装で再現できるようにする。

[既定NLIの保存結果](../jev-local-results-2026-11-06.json)は正常5/9件、対象外・曖昧2/4件、合計7/13件であり、新しい全件一致の基準は未達である。Issue #16は未完了のままとする。[多言語MiniLMの結果](../jev-local-multilingual-results-2026-11-06.json)も全件一致には達しておらず、基準モデルを多言語MiniLMへ独断で変更しない。

未使用の言い換え入力による過適合の確認は、追加検証案として残す。今回合意した全件一致の基準とは別であり、必須の完了条件へ追加しない。

## Issue #4・#15への引き渡しと未確定の配置

Issue #4は、Issue #16で整えたモデル・入出力・ホスト側検証を本実装へ組み込む。推論サーバの配置とアプリからの呼び出し経路は、Issue #4で具体化する未確定事項である。開発機で動いたことから、既存のLambda構成で重みの導入・推論が成立したとは扱わない。

既存プローブにはAPIキーによる自動切替が残る。正式MVPが呼び出すローカルモデルと接続先はIssue #4で明示し、検証用の自動切替をそのまま正式MVPのモデル選択とみなさない。

Issue #15は、実際にMVPで使うローカルモデルと本実装の経路で、応答30秒以内という条件を正式に実測する。開発用プローブの呼び出し時間を、ブラウザを含む正式な実測の結果へ読み替えない。

## 影響と検証状況

- MVP・関連ADR・引き継ぎ記録は、今回決めたモデル・分類基準・機能範囲と整合させる。公式Jevを正式MVPの前提としていた記述は、延期後の方針と区別する。
- ローカルモデルの推論配置と運用条件は別途確認する。モデル重みの導入、起動、資源使用量、API経路を含む実測が正式MVPの構成で済んだとは扱わない。
- 既存の利用者ホストでの結果はモデル別の記録として保持する。いずれも13件全件一致や正式MVPの動作・性能評価の成功へ読み替えない。
- この文書化では新たなモデルの取得・推論や公式Jevへの接続は行っておらず、合格する検証結果を新しく得たとは扱わない。
