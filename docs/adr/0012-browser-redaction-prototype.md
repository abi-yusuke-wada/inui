# ADR-0012 文章の伏せ字をブラウザで試作する

- 状態は提案。試作を使って置き換え規則を確認する。
- 関連は [Issue #38](https://github.com/abi-yusuke-wada/inui/issues/38) と [ADR-0009](0009-feature-packages-and-subject-change.md)。

## 背景

TeamsやBacklogからコピーした文章を共有する前に、氏名や顧客・システムを特定できる語を確認し、伏せ字に置き換えたMarkdownを作る。試作には架空の文章を使う。

## 比較

| 案 | 費用・作業負担 |
| --- | --- |
| ブラウザ内で規則と利用者が指定した語を照合する | 追加依存とAPI利用料がない。コピー元ごとの規則の保守と、伏せ漏れの目視確認が必要 |
| ローカルの業務APIで同じ処理をする | APIと本文の取り扱いを実装・検証する負担が増える。ローカルの辞書やモデルは利用しやすい |
| ローカルで形態素解析や固有表現抽出を使う | 辞書・モデルの配布量やCPU負荷が増える。未知の人名を検出できるかはサンプルで評価が必要 |

## 試作の内容と影響

- 追加依存なしで、選んだコピー元の形式、敬称、連絡先の形式、認証情報のラベル、手入力の語句を使う。Teamsグループでは発言者名から姓の候補を探し、一意に対応する場合に同じ仮名を割り当てる。同姓が複数なら別の候補として確認に出す。
- Teamsは空行で会話を区切る。グループでは「事項」「手順」などで終わる見出しの行を本文に残す。Backlogは架空の担当者欄などを使って検証する。実際のBacklogのコピー形式とTeamsの返信・メンションは、追加のサンプルで確かめる。
- 本文と置き換えの対応はページのメモリに置き、候補を解除したり、追加の語句を再分析したりできる。出力の確認後にコピーできる。プレビューの通信ポリシーでAPIへの接続を禁止する。
- 同じ語が複数の規則に当たる場合は一つの候補にする。選択済みの範囲が重なれば全体を一度に置き換える。認証情報は英語の `TOKEN`・`PASSWORD`・`API_KEY` と、これらで終わる環境変数名なども検出する。引用符で囲まれた値は改行も含めてまとめて伏せる。
- アプリへの組み込み時に、検出規則、候補の確認方法、Intentと入力例を改めて合意する。Intentの追加と実NLIの再検証は [Issue #32](https://github.com/abi-yusuke-wada/inui/issues/32) と調整する。

## 試し方

devShellで `make app-redaction-preview` を実行し、`http://127.0.0.1:8788/` を開く。「架空の例を入れる」で各形式を試せる。ビルドには既存のesbuildを使う。
