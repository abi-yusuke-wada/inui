# ADR-0009: 業務機能をパッケージに分け、題材を文書・タスク・ホワイトボードへ入れ替える

- 状態: 構成（機能パッケージ・依存の方針・連携先の扱い）は決定（2026-11-16、利用者の回答による）。題材・入力例・完了条件はMVP.mdで案とし、Issue #10のPRのレビューで合意する。
- 関連: [Issue #10](https://github.com/abi-yusuke-wada/inui/issues/10)、[MVP](../../MVP.md)、[ADR-0003](0003-separate-core-from-poc-app.md)、[ADR-0008](0008-local-poc-workflows.md)、[実行手順](../poc-local.md)

## 背景

ADR-0008で実装した休暇申請・交通費精算・申請状況の確認は、利用者（システムエンジニア）が普段使う機能ではなかった。Issue #10のコメント（2026-11-16）で、長いMarkdownを読みやすく表示する画面部品が提案された。利用者は、Markdownの表示、作成済みの予定比較、GitHub・Backlogのチケットと自分のタスクをまとめるタスク画面の3つを題材とし、申請系の画面・API・Intentは破棄してよいと判断した。

利用者は、業務APIはすぐに切り離せる前提で作るため、業務APIの中で依存が増えることはある程度許容する一方、コア（JEVによる判定・ルーティング）と、BFF・`App.tsx`のような入口には大きな依存を持ち込まない方針を示した。

## 比較した案と費用

### 業務機能の置き場所

| 案 | 費用・作業負担 | 判断 |
| --- | --- | --- |
| 機能ごとのworkspaceパッケージ（`packages/features/<機能>`）に業務API・画面・依存をまとめる | package.jsonが機能ごとに増える。ビルド・テスト・lintの対象の指定が必要 | 採用（利用者の選択）。依存が機能のpackage.jsonに閉じ、機能ごとに切り離せる |
| ルートの`src/features/<機能>`へ置き、依存はルートのpackage.jsonに書く | 構成は単純だが、切り離すときに依存を仕分け直す必要がある | 不採用 |
| 従来どおり`src/`の1ファイル群に機能を足す | 追加の構成は不要だが、機能の依存が入口へ混ざる | 不採用 |

### Markdownの変換

| 案 | 費用・作業負担 | 判断 |
| --- | --- | --- |
| 依存なしの簡易変換 | 依存は増えないが、表・入れ子のフェンス等の対応と無害化を自前で保守する | 不採用 |
| markdown-it と DOMPurify | 2つの依存（MIT、MPL-2.0またはApache-2.0）。生のHTMLを無効にし、変換結果を無害化する | 採用 |
| 上記に Mermaid を加える | 間接依存（d3・cytoscape・katex等）を含め約5MBのチャンクが増える。図を含む文書を開いたときだけ読み込む | 採用（利用者の選択） |

### GitHub・Backlogのチケット

| 案 | 費用・作業負担 | 判断 |
| --- | --- | --- |
| 架空のサンプルを返すモックの業務API | 認証・通信・料金は不要だが、普段使う機能にならない | 不採用 |
| 実際のAPIから読み取る（読み取り専用） | 利用者がトークン・APIキーを用意する。GitHub REST APIとBacklog API v2の利用制限の範囲で使う。追加の利用料は想定しないが、各サービスの契約・制限に依存する | 採用（利用者の選択） |
| GitLab・Notion等も接続する | 接続先ごとの認証・検証が増える | 今回は見送り。必要になった時点で別のIssueで検討する |

## 決定

- 業務機能は`packages/features/`のworkspaceパッケージに分ける。`schedule`（予定比較。PR #25の実装を移動。2026-11-18に削除）、`markdown`（Markdownの表示）、`tasks`（タスク）、共通の小さな部品の`kit`（本文サイズを制限したJSONの読み取り、同一オリジンのfetch、要求の取り消し、エラー表示）とする。各パッケージは業務API（Honoのサブアプリ）・画面（React）・テストと、その機能だけで使う依存を持つ。
- 入口（`src/`）は、各パッケージの業務APIを`/api`へ組み込み、画面を`React.lazy`で遅延読み込みするだけとする。ブラウザのビルドはesbuildのcode splittingで業務画面を`dist/public/assets/`のチャンクへ分け、サーバーは生成された名前のチャンクだけを配信する。入口の`app.js`（約220KB）にMermaid等は含めない。CSSは小さいため最初の`app.css`へまとめる。
- コア（`packages/core`）の候補は、申請系の3つを削除し、`markdown_view`・`task_board`・`schedule_compare`と案内用の3つ（対象外の機能・対象外の操作・曖昧）の6候補とする（予定比較は2026-11-18に削除し、ホワイトボードを加えた現在も6候補）。曖昧な入力のwire名は`unspecified_request`とし、内部の`clarify`へ対応付ける。質問文は採用済みのものを使う。
- 申請系の画面・API・保存（`applications`テーブル）を削除する。既存の`.local-poc/app.sqlite`に残る`applications`テーブルは読み書きしない。自分のタスクは同じファイルの`local_tasks`テーブルへ保存する。
- GitHubは、自分が担当のIssue、自分が作ったPR、レビューを依頼されたPRを検索APIで読み取る。Backlogは、自分が担当の未完了の課題を読み取る（2026-11-18に削除）。どちらも読み取り専用で、取得結果は保存しない。リダイレクトに従わず、10秒で打ち切る。応答は項目・リンク先（`https://github.com/`、`https://<スペース>.backlog.jp|com/view/`）・制御文字を検証し、失敗は固定のコードと案内文へ置き換える。
- 認証情報は、利用者が環境変数`INUI_GITHUB_TOKEN`・`INUI_BACKLOG_SPACE`・`INUI_BACKLOG_API_KEY`で与えた場合だけ使う。`make app-dev`の起動スクリプトは、この3つだけをアプリのプロセスへ渡し、推論サーバーには渡さない（Backlogの削除後は`INUI_GITHUB_TOKEN`だけ）。既存の`GH_TOKEN`・`GITHUB_TOKEN`は引き継がない。値はログ・エラー・応答へ含めない。BacklogのAPIキーはAPIの仕様でクエリに入るため、URLを記録しない。
- 画面が失敗の種類を区別できるよう、BFFはエラー応答に固定のコードを`X-Error-Code`ヘッダーとして付ける。画面はエラー本文を読まない（ADR-0008の方針を維持）。
- Markdownのファイルはブラウザ内だけで読み、サーバーへ送らない。markdown-itで生のHTMLを無効にし、DOMPurifyで無害化してから表示する。画像は外部への通信を起こさないよう表示しない。Mermaidは`securityLevel: strict`で描画し、生成したSVGも無害化する（ラベルを作る`foreignObject`の中のHTMLは許可する）。画像（`img:`）・URL・`url()`を参照する図は、描画の途中で画像の読み込みが始まり外部へ通信するため、描画せずに定義を表示する（2026-11-18、CodeRabbitの指摘で追加）。
- 依存の取得は従来どおりNixのdevShellのpnpmで行い、lockfileで版を固定する。依存定義の変更をネットワーク経由でlockへ反映する`make app-lock-update`を追加した。`pnpm-workspace.yaml`の`minimumReleaseAge`で、公開から14日未満の版を解決しない。PR #25で導入済みの8件（hono 4.13.17等）は、その版に限り除外する。
- worktreeでも本体のチェックアウトと同じpnpmストア・メタデータキャッシュ（`<本体>/.local-poc/`）と、実NLIのモデル（`<本体>/.local-jev/`、`make app-model-check`）を使う。ストアからはハードリンクで配置されるため、パッケージの実体は重複しない。

## ホワイトボードの追加（2026-11-17）

- 状態: 決定（利用者の回答による）。Issue #10の本文には追加機能を個別のIssueにするとあるが、利用者の判断でこのPRに含める。
- 背景: 実ブラウザでの確認中に、利用者からホワイトボードの画面で絵を描けるようにしたいという依頼があった。

| 案 | 費用・作業負担 | 判断 |
| --- | --- | --- |
| Excalidraw（MIT）を使う | 手書き・図形・矢印・文字・取り消し・PNG/SVG書き出しがそろう。依存は大きく（`dist/prod`で約18MB、うち中国語・日本語用のフォントXiaolaiが13MB）、lockfileは約1,400行増える | 採用（利用者の選択） |
| 依存なしでcanvasを自作する | 軽いが、ペン・消しゴム・色・取り消し・PNG書き出し程度に限られる | 不採用 |
| tldrawを使う | 高機能だが独自ライセンスで、本番利用にはライセンスキーが必要 | 不採用 |

- 決定:
  - `packages/features/whiteboard`に、ボードの業務API（作成・一覧・読み込み・保存・削除）と画面を置く。ボードは名前と描画内容（Excalidrawの要素・画像・背景色）をSQLiteの`whiteboards`テーブルへ保存する。保存は利用者が「保存」を押したときだけ行い、1回の本文は8MBまでとする。要素の中身はExcalidrawの形式のまま保存し、表示時にExcalidrawのrestoreで検証させる。
  - Excalidrawは、画面を開いたときだけ遅延読み込みする。CSS（144KB）は入口の`app.css`に入れず、ビルド時にフォントとあわせて`dist/public/excalidraw/`へコピーし、画面を開いたときに読み込む。`window.EXCALIDRAW_ASSET_PATH`を`/excalidraw/`に向け、フォントを外部のCDN（esm.sh）から読まないようにする。Excalidrawは配信に失敗したときだけ既定の配信元を試すため、外部への通信を完全には禁止していない。
  - ボードを開いた直後はペン（freedraw）を選び、ドラッグでそのまま線を描けるようにする。Excalidrawのファイルを開く・上書き保存するメニューは無効にする。
  - コアに`whiteboard`を加えて7候補とする（2026-11-18に予定比較を削除して6候補）。音声入力ではMarkdownがカタカナになるため、Markdownの表示の候補説明に「マークダウン」を加えた。
  - 画面のテストでは、JSDOMでcanvasを描画できないため、Excalidrawを保存・読み込みのAPIだけを再現するスタブに置き換える（esbuildのalias）。実際の描画は実ブラウザで確認する。
- 影響: Excalidraw 0.18.1が依存する古いRadixの部品は、peerとしてReact 19を許可していない（`pnpm peers check`で警告）。Excalidraw自体はReact 19に対応しており、動作は実ブラウザで確認する。

## タスクの看板表示（2026-11-17）

- 状態: 決定（利用者の回答による）。
- 自分のタスクに状態（`todo`・`doing`・`done`）を加え、Todo表示と看板表示を切り替えられるようにする。以前の`local_tasks`（完了の真偽だけ）は、起動時に未完了を`todo`、完了を`done`へ移す。`done`の列は互換のため状態と同じ内容で保つ。
- 看板に載せるのは自分のタスクだけとし、GitHub・Backlogのチケットは「参照のみ」の欄に残す。看板で連携先のチケットを動かすと、inuiから閉じる意図に見え、元のサービスとの二重管理になるため（利用者の判断）。列名は、連携先のBacklogと紛らわしくないよう「To do・Doing・Done」とする。
- カードの移動は、ブラウザ標準のドラッグ＆ドロップと「←」「→」のボタンで行う。依存は追加しない。タッチ操作でのドラッグと、列の中での並べ替えは対象外とする。

## 予定比較の削除（2026-11-18）

- 状態: 決定（利用者の判断による）。
- 背景: 利用者は会社の仕事をしながらinuiを使う想定で、社内の予定はグループウェアで管理している。グループウェアとAPIで連携して予定を参照するのは現実的でなく、サンプルの社員・予定を比べる画面は使わなくなる見込みとなった。

| 案 | 費用・作業負担 | 判断 |
| --- | --- | --- |
| グループウェアのAPIと連携して予定を参照する | 社内のグループウェアとの接続・認証の調整が要り、現実的でない | 不採用（利用者の判断） |
| サンプルの社員・予定のまま残す | 保守は少ないが、普段使う機能にならず、比較の題材として意味が薄い | 不採用 |
| 画面・API・Intentごと削除する | 候補の説明を変えるため、実NLIで分類を検証し直す | 採用 |

- 決定:
  - `packages/features/schedule`（予定比較の画面・社員と予定の業務API・人名の照合）を削除し、コアから`schedule_compare`を外して6候補とする。BFFの判定の応答から人名の選択（`people`）を外し、画面への引数を渡す経路をなくす。
  - 予定の確認を求める入力は対象外の機能、予定の登録・削除は対象外の操作として案内する。対象外の機能の説明から「社員の予定比較」を外し、例に「社員の予定の確認」を加えた。曖昧入力の説明は、対象の例に「予定」を含めたまま残す（外すと「確認したい」「開いて」が別の候補に分類されたため。比べた案と結果は[実行手順](../poc-local.md)に記録する）。
  - 旧形式の「仕事」の分類は、タスクと会議室予約（対象外の案内）にする。
  - 日付の検証（`kit`の`isValidDate`・`validDate`）は予定比較だけで使っていたため削除した。
- 影響: 入力例は予定比較の4件を外し、予定の確認1件を対象外の機能として加えた20入力（画面12・案内8）になる。人名の選択の集計（4/4件）は完了条件から外す。`make app-diagnose`のアプリの確認は、社員一覧の代わりに`/api/health`の応答（アプリ名とビルドID）で行う。

## 入力欄の配置と業務画面の全画面表示（2026-11-18）

- 状態: 決定（利用者の回答による）。
- 背景: 自然言語の入力欄が常に画面の上部にあり、業務画面（タスクの看板・ホワイトボード等）が狭くなっていた。利用者から、入力欄を右下のチャットボットのようなボタンから開くようにし、業務画面には画面全体を使わせたいという依頼があった。

| 論点 | 案 | 判断 |
| --- | --- | --- |
| 最初の画面 | 中央に入力欄を置き、業務画面を開いた後は右下のボタンへしまう | 採用（利用者の選択）。最初に何をすればよいかが分かる |
| 最初の画面 | 最初から右下のボタンだけを置く | 不採用 |
| パネルの表示 | 入力と結果（開いた画面・案内・エラー）の履歴を残す | 採用（利用者の選択）。再読み込みで消え、40件を超えると古いものから捨てる |
| パネルの表示 | 直前の結果だけを出す | 不採用 |
| 全画面の範囲 | 細いヘッダー（ロゴ・使い方）を残し、フッターは出さない | 採用（利用者の選択） |
| 全画面の範囲 | ヘッダーも消す | 不採用 |

- 決定:
  - 入口の`App.tsx`とCSSだけで実装し、依存は追加しない。業務画面のパッケージは、ホワイトボードの描画領域の高さと、Markdownの本文の幅（読みやすさのため980pxまで）だけを調整した。
  - 業務画面を開いたらパネルを閉じ、画面へフォーカスを移す。パネルを開くと入力欄へフォーカスを移し、Escか「×」で閉じて右下のボタンへ戻す。送信した文は入力欄から消して履歴に残し、失敗したときは「もう一度試す」で同じ文を送り直せる。
  - 送信した時点で前の業務画面を消す方針は変えない（未保存のホワイトボードは確認する）。案内やエラーだけが返った場合は、業務画面のない状態でパネルに表示する。
  - ホワイトボードは右下にExcalidrawのボタンがあるため、右下のボタンを上にずらす。
  - 旧形式も業務画面を画面全体に表示し、メニューへ戻るボタンをヘッダーに置く。旧形式に右下のボタンは置かない。
- 影響: 自然言語UIでは、2つ目以降の用件の前にパネルを開く操作が1回増える。旧形式との操作回数の比較では、この操作の数え方をIssue #15で決める。画面のテストはJSDOMで行い、レイアウトと重なりは実ブラウザで確認する。

## Backlogの連携の削除（2026-11-18）

- 状態: 決定（利用者の判断による）。
- 背景: 利用者から、タスク画面でのBacklogの参照は不要で、GitHubだけでよいとの指示があった。GitHubは、自分が担当のIssueに加え、自分が作ったPR・レビューを依頼されたPRも残すことを確認した。

| 案 | 費用・作業負担 | 判断 |
| --- | --- | --- |
| Backlogの連携を残す | APIキーの管理と、顧客の情報を含み得る課題の扱いが続く | 不採用（利用者の判断） |
| Backlogを外し、GitHubのIssue・PRを残す | 判定の説明を変えるため、実NLIで分類を検証し直す | 採用（利用者の選択） |
| GitHubもIssueだけにする（PRも外す） | 「レビュー待ちのプルリクを確認したい」も対象外にするため、判定の説明と入力例がさらに変わる | 不採用（利用者の選択） |

- 決定:
  - `packages/features/tasks`からBacklogの読み取り（`backlog.ts`・`/api/tasks/backlog`・設定の読み込み）を削除する。起動スクリプトがアプリへ渡す認証情報は`INUI_GITHUB_TOKEN`だけにし、以前の`INUI_BACKLOG_SPACE`・`INUI_BACKLOG_API_KEY`が設定されていても読まない・渡さない。
  - タスク画面は自分のタスクとGitHubの2つの欄にする。看板表示では自分のタスクを横幅いっぱいに広げ、GitHubの欄を下に置く。
  - コアのタスクの説明から「Backlogの課題」を外し、対象外の機能の例に「Backlogの課題の確認」を加える。例を加えずに外すだけでは、「Backlogの課題を見たい」がタスク画面に分類された（比べた案と結果は[実行手順](../poc-local.md)に記録する）。
- 影響: 入力例は「Backlogの課題を見たい」をタスク画面から対象外の機能へ移し、20入力（画面11・案内9）になる。看板の列名（To do・Doing・Done）は、Backlogと紛らわしくないよう決めたものだが、変える理由はないためそのままとする。

## 影響と未決事項

- 追加した依存はmarkdown-it 15.0.3・dompurify 3.4.17・mermaid 12.2.0（それぞれ公開から2週間以上）。間接依存を含めてlockfileが約1,000行増えた。ライセンス費用はなく、取得時の通信・ディスクは必要。
- 実NLIの分類は、新しい20入力で検証し直した（結果は[実行手順](../poc-local.md)と保存応答に記録する）。申請題材の13入力・19入力の記録は履歴として残し、現行の判定には使わない。
- GitHubへの実接続は、利用者が認証情報を設定した端末で確認する。エージェントは認証情報を読まないため、自動テストは応答を差し替えた確認に限る。
- GitHubの検索APIは、Enterprise Server等の別ホストに対応しない。
- 旧形式のメニューは、文書・仕事の2分類にした。操作回数の数え方と比較の実施はIssue #15で扱う。
- 部署展開時の認証情報の管理（Secrets等）と、Turso・Lambdaでの保存はIssue #12〜#14で扱う。
