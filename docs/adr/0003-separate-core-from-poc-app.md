# ADR-0003: Intent判定のコアをPoCアプリから分離する

- 状態: 決定（2026-11-02）。コアの責務の記載を、JEV優先の方針（[ADR-0004](0004-jev-first-intent-routing.md)）に合わせて更新（2026-11-04）
- 関連: [Issue #4](https://github.com/abi-yusuke-wada/inui/issues/4)、[ADR-0001](0001-mvp-hosting-and-storage.md)、[ADR-0004](0004-jev-first-intent-routing.md)、[MVP](../../MVP.md)

2026-11-06更新: パッケージとしてコアを分離する判断は維持し、採用モデルとMVPの対象は[ADR-0006](0006-local-model-for-mvp.md)を優先する。正式MVPは`nli-deberta-large`によるIntent分類と3画面の選択に限定し、公式Jev・引数の自動補完・MCPは部署展開と社内費用承認の後へ延期する。以下の比較案は当初の判断の履歴であり、ローカル推論の配置まで同じLambdaへ決定したものではない。

## 背景

Issue #4で実装するアプリ（UI・Hono / Lambda・認証・業務API・DB）は、MVPの検証用のPoCであり、検証後に捨てる・作り直す前提とする。一方、採用した推論モデルを呼び出して入力を判定し、その結果を許可リストで検証する処理は、inuiの検証対象そのものであり、PoCアプリを捨てた後も使い続けるコアである。

両者が同じコードに混在すると、PoCアプリを捨てるときにコアも作り直しになる。また、JEVの接続方法を変えたり、LLMを追加したりするたびに、アプリ側の修正が必要になる。

## 比較した案

| 案 | 費用 | 評価 |
| --- | --- | --- |
| A. アプリ内にLLM・JEVの呼び出しと判断処理を直接実装する | 追加費用なし | 最も早く作れるが、アプリを捨てるとコアも失われる。LLM・JEVの変更がアプリ全体に波及する |
| B. コアを独立したパッケージとし、アプリはその公開インターフェースだけを呼ぶ | 追加費用なし。同じLambdaにまとめて配布できる | アプリとコアを別々に捨てる・差し替えることができる。境界の型定義の手間が増える |
| C. コアを別のサービス（別Lambda・別API）として配置する | Lambda・API入口・通信が増え、構築・運用の手間も増える | 分離は最も強いが、低頻度のMVPには過剰。30秒の応答時間の上限にも通信が加わる |

## 決定

案Bを採用する。

- コアは独立したパッケージとして実装し、アプリ（UI・Hono・認証・業務API・DB）に依存しない。依存の向きはアプリ → コアの一方向とする。
- コアの責務: 入力テキストと許可リストを受け取り、固定したローカル実NLIのIntentを検証して返す。MVPでは日付・金額・区分・状態を自然言語から抽出せず、LLMも使わない。HTML・JavaScriptは生成しない（[ADR-0006](0006-local-model-for-mvp.md)）。
- アプリの責務: 入力受付・認証・認可、検証済みIntentに基づく事前実装済みの3画面の表示、フォーム・一覧での日付・金額・区分・状態の明示操作、保存前のユーザー確定と業務API・DBの実行。Intent・Tool・UIと画面から渡す引数の許可リスト・入力検証をホスト側で維持する。
- 採用モデルとの接続は、コア内の接続部分（アダプター）に閉じ込め、接続先の変更がコアの判断処理とアプリに波及しないようにする。公式Jevとの接続は延期後の作業とする。将来の補助判定や比較を追加する場合も別途判断し、抽象化はこの境界に限り、それ以外には汎用的な仕組みを作らない。
- 当初はアプリとコアを同じLambdaへ配布する方針だった。パッケージの分離は維持するが、ローカル推論サーバーの配置とMVPからの呼び出し経路はIssue #4で具体化する。重みの導入・推論が既存Lambda構成で動作することは未検証であり、配置を確定しない（[ADR-0006](0006-local-model-for-mvp.md)）。

## 影響

- Issue #4では、コアとアプリを別のパッケージ（pnpmのworkspace等）として構成する。具体的なディレクトリ名・パッケージ名は実装時に決める。
- コアの入出力の型（判断結果・検証エラー）を最初に定義し、アプリはその型だけに依存する。
- コアは、推論モデルを固定の応答に差し替えた単体テストで、アプリなしに検証できるようにする。実際のMVPは実NLIを使い、単体テストを分類精度の実測と扱わない。MVPの未対応・失敗ケースと、各境界の未許可Intent・Tool・UI・引数の検証を行う。
- PoCアプリを捨てる場合も、コアのパッケージとテストはそのまま残る。
