# ADR-0004: Intent判定をJEV優先で行い、MVPではLLMを使わない

- 状態: 決定（2026-11-04）。JEVへの接続検証（[Issue #16](https://github.com/abi-yusuke-wada/inui/issues/16)）で前提が崩れた場合は見直す
- 関連: [Issue #11](https://github.com/abi-yusuke-wada/inui/issues/11)、[Issue #9](https://github.com/abi-yusuke-wada/inui/issues/9)、[ADR-0001](0001-mvp-hosting-and-storage.md)、[ADR-0003](0003-separate-core-from-poc-app.md)、[MVP](../../MVP.md)

## 背景

README・MVP・ADR-0001/0003は「LLM・JEV」を並べて記載し、どちらを主とするかを決めていなかった。

inuiの問題提起は「LLMにどんなUIを生成させるか」ではない。LLMは応答が遅く、費用もかさむ。JEVのように安く速く使えるルーターで入力を適切な画面へ振り分けるだけで、これまでのUI/UXを最適化できるのではないか、という点にある。研究の問いは「安く速いルーター（JEV）による振り分けで、これまでのUI/UXを最適化できるか」とする（[README](../../README.md)）。

Issue #9では、JEVが判定とルーティングを担い、判断結果をホスト側の許可リストで検証することを決めた。JEVがどの候補にも当てはまらないと判定した入力（fallback）をLLMに回すかどうかは、この判断に委ねていた。

## 比較した案

| 案 | 費用 | 評価 |
| --- | --- | --- |
| A. JEVだけで判定し、MVPではLLMを使わない（採用） | LLMの利用料はかからない。JEVの利用料は別途相談（ADR-0001と同じ扱い） | JEVの振り分けの実力をそのまま評価できる。JEVが判定できない入力は、LLMなら補える場合も案内になる |
| B. JEVを主とし、判定できない入力をLLMで補う | 補助判定のたびにLLMの利用料がかかる。APIキーの管理と、提供元・モデルの選定が加わる | 判定できる入力は増えるが、JEVの結果にLLMの補助が混ざり、振り分けの効果を切り分けにくい。30秒の上限の中でJEVとLLMを続けて呼ぶ時間配分も必要になる |
| C. LLMを応答時間・費用の比較対象としてのみ使う | 比較計測の回数分のLLMの利用料がかかる | 「LLMは遅く高い」という前提を数値で確かめられるが、MVPの完了には不要 |

## 決定

案Aを採用する。

- Intent判定はJEVだけで行う。JEVは判断結果（Intentと引数）を返し、ホスト側が許可リストで検証する（Issue #9）。
- JEVがどの候補にも当てはまらないと判定した入力は、LLMに回さず、対象外または再入力の案内にする。
- JEVとの接続はコアの接続部分（アダプター）に閉じ込める（ADR-0003）。あとから案Bの補助判定や案Cの比較計測を足す場合も、アプリを変えずに済むようにする。案Cは、必要になった時点でIssue #15・#5で追加を判断する。
- JEVの具体的な製品・接続先・出力の形式と、判定できない入力の表し方は、Issue #16で実際に接続して確かめる。

次のいずれかが分かった場合は、この判断を見直す。

- JEVがMVPの入力例を判定できない
- JEVを含む1回の応答が30秒に収まらない

## 影響

- MVP.md: LLMの記載をJEVに揃え、30秒の判定は「JEVを含む1回の応答」とする。JEVが判定できない入力の案内を、未対応ケースに加える。
- ADR-0003: コアの責務の「LLM・JEVを呼び出す」を、JEVを呼び出す記載に改める。
- ADR-0001: LLMに関する記載（外部リソースの利用、APIキーの利用料など）は、MVP以降にLLMを使う場合の前提として残す。
- Issue #9: fallbackをLLMに回すかの論点は、「回さずに案内する」で決まる。判断結果の型の `decidedBy` を残すかは、案B・Cを足す可能性を踏まえて実装時に決める。
- Issue #16: MVPではLLMの提供元・モデルを選定しない。
- Issue #15: 「JEVで判定したか、LLMの補助で判定したか」の記録は、MVPでは不要になる。
